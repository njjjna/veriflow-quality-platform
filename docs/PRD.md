# VeriFlow v0.3 — 产品需求文档（PRD）

**状态**：拟定需求基线，待业务方评审签字；**假设业务**，没有任何真实医院客户参与。

## 1. 问题陈述

在多机构系统上线准备阶段，缺陷、接口质量异常和UAT证据分散于不同人员及表格。若无法区分“问题已被提出”和“问题已经复测关闭”，项目负责人难以判断当前是否满足预定义的上线门槛。

业务目标：使发现、分派、整改、复测、验收、汇报各环节可追溯，并提供对不同角色的最小必要授权。

## 2. 业务对象及范围

- **客户背景**：虚构的医疗信息化集成服务商；仅以机构与接口**模拟数据**为例。
- **用户**：平台管理员、项目经理、测试工程师、整改负责人、业务验收人、只读体验者。
- **核心对象**：用户、项目、项目成员、工单、数据质量检查批次、UAT验收项、审计事件。
- **不在范围内**：真实医疗接口、患者资料、费用结算、HIPAA/PDPA认证承诺、医院临床决策、SOC系统、完整风险评级方法。

## 4. 业务关键规则（2026-11-21用户已确认）

1. **工单状态**：`open → in_progress → ready_for_retest → closed`；复测失败 `ready_for_retest → in_progress`；不得直接 `open → closed`。
2. **整改提交**：至少5字整改说明；整改人只能操作分配给自己的问题，项目经理可以跟进。
3. **独立复测**：实施负责人不能复测本人负责的工单；测试人员/经理可以复测（经理与实施同一人时禁止）。
4. **UAT职责分离**：测试人员执行（通过/不通过），记录证据；业务验收人审核；同一用户不能执行和审核同一条。
5. **上线门禁与审批**：无高/紧急未关闭工单、全部8项UAT独立审核通过、最新数据检查0异常、经理确认安全复核/回滚演练/备份恢复/交付文档/运维交接并提供证据编号；如存在低/中级遗留问题，经理须说明风险接受理由；验收负责人独立审核，审核前重新计算门禁。*流程状态approved不等于真实生产安全准入或实际部署完成*。
6. **数据质量指标**：通过率 = 未触发任何规则的**记录数** / 总记录数；不是模型Accuracy，也不是字段级合格率。
7. **默认封闭注册**：普通用户由管理员创建账号，再授予项目角色；不得绕过后台权限检查。
8. **双模式设计**：`VERIFLOW_MODE=demo` 允许项目成员多角色组合，方便演示；`VERIFLOW_MODE=production` 同一项目每个账号仅可有1个业务角色，平台管理员不可绕过业务职责限制。两种模式均要求UAT执行人≠审核人，整改负责人≠复测人，上线申请人≠审核人。模式只能在服务器启动前配置，不能由前端用户自由切换。**严格角色模式不表示整个系统可以用于企业生产**。
9. **附件证据**：只有授权项目成员可读取，测试员上传UAT证据，经理/测试员/经办整改人上传工单证据；已通过UAT或关闭工单不允许直接追加附件。每个文件≤5MB，仅PNG/JPEG/PDF；图片可在受控链接预览，PDF下载；附件不放在公开静态目录。公开发布前仍需安全扫描、防病毒、防篡改存储、配额、保留策略、备份及删除机制。

## 5. 非功能需求（部分尚待验证）

- 功能正确性：需要测试关键业务路径和权限拒绝路径。
- 可追溯性：关键变更记录操作主体与时间。
- 安全性：最小权限、会话保护、密码哈希、CSRF检查、项目隔离（详见 `production_gap.md`）。
- 可维护性：分离业务规则、数据模型和UI；配置不写死秘密；自动化CI。
- 可复现性：给出模拟样本、可运行命令、预期结果、测试命令和Docker配置。
- 可用性：中文清晰提示、输入校验、导出反馈；尚需人工可用性测试与WCAG审查。

## 6. 已通过评审的决策 / 尚待后续评审

- **已确认**：演示模式角色可兼任，严格职责模式单人单项目单职责；无论何种模式，执行与复核/审批必须不同人员。
- **已确认**：UAT支持文字和附件证据、预览及授权控制；当前只有基本本地附件，尚无对象存储和防病毒。
- **已确认**：上线需要安全风险复核、数据质量、备份/回滚、交付文档等条件，结合质量检查与独立审批。
- **待确认**：风险接受权限、上线准入的数值阈值是否按项目定制、电子签名、保留期限、部署所在区域。
- 真实部署在哪个区域，是否需要跨境数据传输？本演示不接入真实数据，也没有这类需要。
