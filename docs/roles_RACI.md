# 干系人分析、RACI与角色权限（v0.3）

**适用范围**：假设医疗信息化集成项目；角色基于职责设计，不代表任何真实公司的组织架构。

## 角色与痛点

| 角色 | 业务目标 | 平时查看什么 | 必须完成的动作 |
|---|---|---|---|
| 平台管理员 | 账号安全与组织配置 | 用户、成员、项目、关键操作 | 创建用户/项目、授予角色、停用账号 |
| 项目经理 | 保证交付进度，明确责任 | 高风险问题、UAT通过情况、逾期任务 | 问题分配、进度跟踪、汇报 |
| 测试工程师 | 可追溯地发现与复测缺陷 | 工单、测试结果、质量检查批次 | 登记问题、数据检查、复测、UAT执行 |
| 整改负责人 | 明确工作量并提交整改 | 分给自己的缺陷及要求 | 处理、填写整改说明并申请复测 |
| 业务验收人 | 判断业务目标是否满足 | UAT证据、阻断问题、结果 | 审核UAT、通过或驳回 |
| 只读体验者 | 了解系统功能 | 分配项目下的数据和摘要 | 仅浏览，不能更改数据 |

## 权限矩阵（本版实际行为）

| 能力 | 管理员 | 经理 | 测试 | 整改 | 验收 | 只读 |
|---|:---:|:---:|:---:|:---:|:---:|:---:|
| 查看本项目看板/工单/UAT | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| 创建工单 | ✓ | ✓ | ✓ | — | — | — |
| 分配工单 | ✓ | ✓ | — | — | — | — |
| 开始整改/提交整改 | ✓ | ✓ | — | 本人负责 | — | — |
| 独立复测并关闭/退回 | ✓* | ✓* | ✓* | — | — | — |
| 数据质量检查并转工单 | ✓ | ✓ | ✓ | — | — | — |
| UAT执行、证据填写 | ✓ | — | ✓ | — | — | — |
| UAT审核 | ✓* | — | — | — | ✓* | — |
| 导出本项目工单CSV | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| 查看审计日志 | ✓ | ✓ | — | — | ✓ | — |
| 平台创建/停用账号与分配角色 | ✓ | — | — | — | — | — |

*同一用户不能复测本人整改的工单、审核本人执行的UAT，也不能审核本人提交的上线申请。管理员**不是**职责分离规则的例外。

## 双模式决策（用户已确认）

- `demo`：一个项目成员可兼任若干角色（如 `manager,tester`），方便测试；但执行人和审批人仍必须是不同账号/人员，单账号不能模拟自我审批。
- `production`：同一账号在同一个项目只允许一个业务角色；平台管理员只做平台治理，在此模式下被禁止执行工单写入、UAT执行/审核及上线流程等业务动作。**此模式只是更严格的RBAC策略，并不等同达到真正生产发布安全要求**。
- 角色模式在服务端通过环境变量配置，UI只能读取状态，不可自行切换；从含多角色的演示数据库切换到严格模式时会拒绝启动，必须先清理角色数据。推荐使用互相独立的数据库及附件存储。

## RACI样例

R：Responsible，负责执行；A：Accountable，最终负责；C：Consulted，需征询；I：Informed，需告知。

| 任务 | 管理员 | 经理 | 测试 | 整改 | 验收 |
|---|---|---|---|---|---|
| 创建项目及赋权 | R/A | C | I | I | I |
| 设计上线验收计划 | I | A | R | C | C |
| 缺陷登记和优先级评估 | I | A | R | C | I |
| 执行整改 | I | A | C | R | I |
| 独立复测 | I | A | R | C | I |
| 执行UAT | I | A | R | C | C |
| 业务验收审核 | I | C | R（提供证据） | I | A |
| 上线流程准备申请 / 独立审核 | I | R | C | C | A |

说明：v0.3已经提供“经理提交—验收负责人独立审核”的模拟审批流；**它不自动执行真实生产发布，也不证明企业级安全合规**。
